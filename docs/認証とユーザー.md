## 1. 推奨されるシステムアーキテクチャ（3層構成）
認証とユーザー情報は、Temporalの「外側」に配置してAPI経由で連携させます。

* APIゲートウェイ / バックエンド（フロントAPI層）
* ユーザーからのリクエストを直接受け取る。
   * 認証の検証（JWTのデコードなど）や、ユーザープロファイルのCRUD操作を担当。
   * 認証に成功したリクエストのみ、TemporalのWorkflowを起動（Start）する。
* アイデンティティプロバイダー（認証・IdP層）
* Auth0、Cognito、Keycloak、Firebase Authなど。
   * ユーザーのサインアップ、ログイン、トークン（JWT）の発行を担う。
* データベース（ユーザー情報保持層）
* PostgreSQL、MySQL、MongoDBなど。
   * ユーザーの氏名、住所、決済情報など、ワークフロー処理に必要な詳細な属性情報を格納。

------------------------------
## 2. データ連携とセキュリティの実装指針## Temporalに渡すデータは「最小限のID」に絞る
Temporalの履歴（Workflow History）はすべて暗号化やDBに記録されますが、デバッグ時やWeb UI上で生データが見えてしまうリスクがあります。

* ❌ やってはいけないこと: Workflowの引数やStateに、ユーザーのパスワード、クレジットカード情報、個人情報（PII）をそのまま渡す。
* ⭕ 推奨される方法: Workflowを起動する際は、一意の userID や transactionID のみを引数（Input）として渡す。

## ユーザー情報の参照は「Activity」で行う
ワークフローの途中でユーザーの名前やメールアドレスが必要になった場合は、Workflowコード内ではなく、Activity内からユーザーデータベース（またはユーザー管理API）へ問い合わせを行います。

[クライアント] ➔ (ログイン/JWT取得) ➔ [Auth0 / Cognito]
     │
  (リクエスト + JWT)
     ▼
[API バックエンド] (JWT検証 ＆ userID抽出)
     │
     ├─➔ [Temporal Client] ➔ Workflow起動 (引数: userID)
     │
     ▼
[Temporal Worker (Workflow)]
     │
     └─➔ [Activity] ➔ [ユーザーDB] から userID を基に詳細情報を取得して処理

## Temporal Web UI や CLI 自体の認証（運用面）
開発者や運用者がTemporalの管理画面（Web UI）にアクセスする際の認証も必要です。Temporal自体は、OIDC（OpenID Connect）をサポートしています。

* バックエンド側の認証で使っているIdP（Auth0やCognitoなど）とTemporal Web UIをOIDC連携させ、特定のグループやロールを持つ運用者だけがワークフローの監視・転送・強制終了を行えるように制限します。

## 3. メリット

* セキュリティの向上: ワークフローの履歴に個人情報が残らないため、データ漏洩のリスクを最小限に抑えられます。
* 責務の分離: 認証の仕様変更（例: MFAの追加など）があっても、Temporal側のワークフローロジックを修正する必要がありません。
* パフォーマンスの最適化: 大きなユーザーオブジェクトをTemporalのStateに抱え込まずに済むため、メモリや通信のペイロードを軽量に保てます。

## パターンA：Realm（レルム）分離（推奨：B2B向け）
Keycloakの最上位の管理単位である「Realm」を、SaaSのテナントごとに新規作成する方式です。

* 特徴: テナントごとにログイン画面のデザイン、パスワードポリシー、外部IdP（Google、Oktaなど）の連携設定を完全に独立させることができます。
* メリット: SaaS Aの管理者が自社のユーザーを管理する（ユーザーの追加・削除など）「管理権限の委譲」が標準機能で簡単に実現できます。

## パターンB：1つのRealm内でのグループ/ロール分離（B2C、または軽量なB2B向け）
「Platform-Realm」という1つの大きな単位の中で、ユーザー属性（Attributes）やグループ機能を使って tenant_id を割り振る方式です。

* 特徴: ログイン画面や認証設定は全SaaS・全テナントで共通になります。
* メリット: Keycloak自体の運用管理が非常にシンプルになり、大量のテナント（数千〜数万）を省リソースで捌くのに適しています。

------------------------------
## 2. Temporalプラットフォームとの連携イメージ
Keycloakが発行したトークンを、基盤（Temporal）と各SaaSでどのように利用するか。

   1. ログインとJWT発行:
   ユーザーが特定のSaaSにアクセスすると、Keycloakの認証画面へリダイレクトされます。ログイン成功後、KeycloakからJWT（アクセストークン）が発行されます。このトークンには、client_id（どのSaaSか）や、カスタムクレームとして tenant_id が含まれます。
   2. APIゲートウェイでの検証:
   SaaSのバックエンドAPIや、Temporalの手前に配置したAPI Gateway（Kongなど）で、Keycloakの公開鍵を使ってJWTの署名を検証します。
   3. Temporalへのコンテキスト伝播:
   認証されたリクエストがTemporalのWorkflowを起動する際、トークンから抽出した tenant_id と user_id をTemporalの「Header（メタデータ）」にセットして伝播させます。これにより、Activity（各SaaSの処理実体）が「どのテナントのデータとして処理すべきか」を安全に識別できます。

------------------------------
## 3. Keycloakを採用するメリット・デメリット## ⭕ メリット（なぜ選ばれるか）

* ライセンス費用がゼロ: ユーザー数やテナント数が増えても、Auth0などのように従量課金で費用が爆発する心配がありません。
* 圧倒的な機能網羅性: OIDC/OAuth2.0、SAML対応、MFA（多要素認証）、ソーシャルログイン、企業のActive Directoryとの同期など、エンタープライズSaaSに必要な機能が最初からすべて揃っています。
* 拡張性: JavaでSPI（Service Provider Interface）が用意されており、独自の認証ロジックや、既存の特殊なユーザーDBとの連携をコードを書いて拡張できます。

## ❌ デメリット（注意すべき点）

* 運用負荷（インフラ管理）: 高可用性（HA構成）の維持、データベース（PostgreSQL等）のバックアップ、Keycloak自体のバージョンアップやセキュリティパッチ当てを、自社で運用する必要があります。
* 初期の学習コスト: 高機能すぎるがゆえに、設定項目が多く、仕様（Token交換やフロー設定など）を理解するまでに少し時間がかかります。

## 🏛️ 全体アーキテクチャ設計
Temporalのプラクティスに基づき、KeycloakへのAPIリクエストなど成否が不確定な外部通信はすべて「Activity」として実装し、全体の登録フローを「Workflow」で統制します。

   1. SaaS フロントエンド: ユーザー登録リクエストを送信。
   2. User Service (Temporal Client): リクエストを受け取り、Temporalの登録ワークフローを開始。
   3. Temporal Worker: ワークフロー（冪等性の担保、状態管理）とアクティビティ（Keycloak API呼び出し、DB保存、メール送信）を実行。
   4. Keycloak: プラットフォーム用レルムにユーザー、グループ、属性を生成・紐付け。

------------------------------
## 📝 Keycloakのデータ構造設計
「Platform-Realm」内でのデータ管理は以下のように構成します。

* グループの活用: 各テナントをKeycloak内のグループとして表現します（例: Tenant-A, Tenant-B）。グループに tenant_id 属性を持たせるか、グループ名そのものをテナント識別子にします。
* ユーザー属性（Attributes）の活用: ユーザー作成時に、カスタム属性として tenant_id を付与します。
* アクセストークン（JWT）へのマッピング: ユーザーがログインした際、発行されるJWT（アクセストークン）のクレームに tenant_id が自動で埋め込まれるよう、Keycloak側でUser Attribute Mapper（または Group Membership Mapper）を設定します。これにより、他のマイクロサービスはJWTを検証するだけで「どのテナントのユーザーか」を即座に判別できます。

## 💻 Temporalによる実装コード例（Go言語の場合）

## 1. ワークフロー定義（Workflow）
ユーザー作成の一連のステップを定義します。どこかでエラーが発生した場合は、自動リトライや、必要に応じて補償トランザクション（Sagaパターンによる取り消し処理）を組み込めます。

package user
import (
	"time"
	"go.temporal.io/sdk/workflow"
)
type CreateUserRequest struct {
	TenantID string
	Username string
	Email    string
	Password string
}
func CreateUserWorkflow(ctx workflow.Context, req CreateUserRequest) error {
	options := workflow.ActivityOptions{
		StartToCloseTimeout: 10 * time.Second,
		// 外部API連携のため、適切なリトライポリシーを設定
		RetryPolicy: &temporal.RetryPolicy{
			InitialInterval:    time.Second,
			BackoffCoefficient: 2.0,
			MaximumAttempts:    5,
		},
	}
	ctx = workflow.WithActivityOptions(ctx, options)

	var activities *UserActivities
	var keycloakUserID string

	// ステップ1: Keycloakにユーザーを作成し、属性とグループを割り当てる
	err := workflow.ExecuteActivity(ctx, activities.CreateKeycloakUserActivity, req).Get(ctx, &keycloakUserID)
	if err != nil {
		return err
	}

	// ステップ2: 自社データベース（User ServiceのDB）にユーザー情報を同期
	err = workflow.ExecuteActivity(ctx, activities.SaveUserToLocalDBActivity, req, keycloakUserID).Get(ctx, nil)
	if err != nil {
		// 必要に応じてKeycloakのユーザーを削除する補償アクティビティを呼び出す
		return err
	}

	return nil
}

## ⚙️ Keycloak側の必須設定（Mappers）
SaaSの他のマイクロサービスが「誰がどのテナントに属しているか」を検証できるようにするため、Keycloakのトークン発行設定をカスタマイズします。

   1. 管理コンソールにログインし、「Platform-Realm」を選択。
   2. 左メニューの「Client scopes」を開き、デフォルトのスコープ（例: roles や profile）、または新規作成したSaaS用スコープを選択。
   3. 「Mappers」タブを開き、「Configure a new mapper」をクリック。
   4. マッパータイプから「User Attribute」を選択し、以下のように設定します：
   * Name: tenant_id_mapper
      * User Attribute: tenant_id（ユーザー作成時に指定した属性名）
      * Token Claim Name: tenant_id（JWTの中に埋め込まれるキー名）
      * Claim JSON Type: String
      * Add to ID token / Access token: 両方「ON」
   5. これにより、SaaSアプリに返されるJWTのPayloadに "tenant_id": "xxxxx" が含まれるようになります。各マイクロサービスはこのJWTをデコード・検証するだけでテナントを識別可能です。

## ⚠️ 実装における注意点と対策

* Keycloakへのアクセス集中（Rate Limit）:
単一レルムに数万ユーザーが集中のうえ、 Temporal のアクティビティが大量に並列実行されると、Keycloakがボトルネックになります。Temporal側の Activity Rate Limiting（流量制限） 機能を使って、KeycloakへのAPIリクエスト秒間上限を制御してください。
* アクティビティの冪等性（Idempotency）:
ネットワーク瞬断などで「Keycloak側ではユーザー作成が成功したのに、Temporalへのレスポンスが届かずリトライされた」というケースが起こり得ます。アクティビティの最初で「既に該当のEmail/Usernameのユーザーが存在するか」をKeycloakに問い合わせ、存在すればそのIDを返す、といった重複考慮のロジック（冪等性）を必ず組み込んでください。

## 2. ワークフロー定義 (src/workflows/create-user.ts)
ワークフロー内では、KeycloakのAPIやデータベースを直接操作せず、必ずアクティビティを経由させて実行します。

import { proxyActivities } from '@temporalio/workflow';import type * as keycloakActivities from '../activities/keycloak';import type * as databaseActivities from '../activities/database';import { CreateUserRequest } from '../interfaces/user.interface';
// アクティビティのプロキシを作成（リトライポリシーなどのオプションを設定）const { createKeycloakUserActivity } = proxyActivities<typeof keycloakActivities>({
  startToCloseTimeout: '10 seconds',
  retry: {
    initialInterval: '1 second',
    backoffCoefficient: 2,
    maximumAttempts: 5,
  },
});
const { saveUserToLocalDBActivity } = proxyActivities<typeof databaseActivities>({
  startToCloseTimeout: '5 seconds',
});
/**
 * ユーザー作成の一連の流れを統制するワークフロー
 */export async function createUserWorkflow(req: CreateUserRequest): Promise<string> {
  // ステップ1: Keycloakにユーザーを作成（属性とグループを付与）
  const keycloakUserId = await createKeycloakUserActivity(req);

  // ステップ2: 自社データベースにユーザー情報を同期
  await saveUserToLocalDBActivity(req, keycloakUserId);

  return keycloakUserId;
}

## 3. Keycloakアクティビティ (src/activities/keycloak.ts)
Keycloak公式のAdmin Clientを使って、実際の外部APIリクエストを処理します。

import KcAdminClient from '@keycloak/keycloak-admin-client';import { CreateUserRequest } from '../interfaces/user.interface';
// Keycloakクライアントの初期化（環境変数などから取得）const kcAdminClient = new KcAdminClient({
  baseUrl: process.env.KEYCLOAK_BASE_URL || 'http://localhost:8080',
  realmName: 'master', // 管理用トークンを取得するレルム（通常はmaster）
});
const TARGET_REALM = 'Platform-Realm'; // ユーザーを追加する対象のレルム
/**
 * Keycloakに管理者として認証を通すヘルパー関数
 */async function authenticateAdmin() {
  await kcAdminClient.auth({
    grantType: 'client_credentials',
    clientId: process.env.KEYCLOAK_CLIENT_ID || 'saas-backend-client',
    clientSecret: process.env.KEYCLOAK_CLIENT_SECRET || 'your-client-secret',
  });
}
/**
 * Keycloakにユーザーを作成するアクティビティ（冪等性を担保）
 */export async function createKeycloakUserActivity(req: CreateUserRequest): Promise<string> {
  await authenticateAdmin();

  // ーーー 冪等性（Idempotency）の担保 ーーー
  // リトライ時に重複エラーにならないよう、同一Emailのユーザーが既にいないかチェック
  const existingUsers = await kcAdminClient.users.find({
    realm: TARGET_REALM,
    email: req.email,
  });

  if (existingUsers.length > 0 && existingUsers[0].id) {
    return existingUsers[0].id; // 既に存在すればそのIDを返して正常終了（リトライ対策）
  }

  // ーーー 新規ユーザー作成 ーーー
  const newUser = await kcAdminClient.users.create({
    realm: TARGET_REALM,
    username: req.username,
    email: req.email,
    enabled: true,
    emailVerified: true,
    // attributesにマルチテナント用のtenant_idを格納
    attributes: {
      tenant_id: [req.tenantId],
    },
    credentials: req.password ? [
      {
        type: 'password',
        value: req.password,
        temporary: false,
      },
    ] : [],
  });

  // Keycloak v18以降、createは作成されたオブジェクトのIDを返さない場合があるため
  // レスポンスからIDを取得するか、再検索してIDを確定させます
  if (newUser.id) {
    return newUser.id;
  }
  
  const fetchedUser = await kcAdminClient.users.find({ realm: TARGET_REALM, username: req.username });
  if (fetchedUser[0]?.id) {
    return fetchedUser[0].id;
  }

  throw new Error('Failed to retrieve created Keycloak user ID');
}

      ...keycloakActivities,
      ...databaseActivities,
    },
    taskQueue: 'user-management-queue',

## 🛠️ SaaS側でのJWT（トークン）検証方法
ユーザーがログインに成功すると、KeycloakからJWT（アクセストークン）が発行され、前述のマッパー設定により以下のようなペイロードがSaaS側に渡ってきます。

{
  "sub": "keycloak-user-uuid-1111",
  "preferred_username": "tanaka_taro",
  "email": "tanaka@example.com",
  "tenant_id": "tenant-abc-999"  // マッパーで埋め込まれた値
}

各マイクロサービス（例えば「注文サービス」「決済サービス」など）のミドルウェアでは、Node.jsの jsonwebtoken や jose ライブラリを使用してこのJWTをデコードし、「要求されたリソースのテナントID」と「JWT内の tenant_id」が一致するかチェックするだけで、安全にマルチテナントの認可制御が行えます。
